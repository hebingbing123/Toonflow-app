# 需求文档

## 简介

本文档描述 **drama-quality-benchmark-ops** 功能的需求。这个 spec 聚焦一个在当前仓库里仍明显缺失、但对后续持续优化非常关键的能力：**把“短剧质量优化”从单次主观判断，升级为可回放、可比较、可放行、可控成本的评测与运营闭环。**

当前项目已经具备以下基础：

1. 平台功能闭环、质量预检、局部返工、记忆预算、观察笔记治理、ROI 聚合已经有实现基础。
2. 质量评审已经能按阶段打分，也能关联部分 token 与质量信息。
3. 技能文件、提示词、记忆策略、模型选择仍会持续变化，未来还会不断做质量优化。

但当前仍缺少以下平台级能力：

1. 没有稳定的 **bad case / golden case 样本池**。
2. 没有把同一输入在不同技能版本、提示词版本、记忆策略下做 **可重复对比** 的实验框架。
3. 没有把“观察笔记治理”“记忆预算策略”“ROI 统计”纳入统一放行标准。
4. 没有把“是否值得推广到更多项目”变成可执行的发布门。

因此，本 spec 的目标是：**建立短剧质量基线、实验回放、人工复核、ROI 放行和观察治理的统一体系，让平台后续每次优化都能更稳、更便宜、更少凭感觉。**

平台技术栈：Rust 后端（Axum + SQLx）+ Flutter 前端。当前项目尚未上线，因此本轮需求 **无需为旧实现做向后兼容设计**。

---

## 优化原则

### 原则 1：质量基线优先于实验吞吐

系统 SHALL 优先保证评测样本能真实代表“像不像 AI、会不会穿帮、情绪是否生硬、人物是否稳定”，而不是为了多跑样本牺牲评测有效性。

### 原则 2：实验成本必须可控

系统 SHALL 避免把每次小改动都升级为全量高成本回放；应优先使用分层样本、缓存、复用中间产物和轻重分级评测，减少无意义 token 消耗。

### 原则 3：观察笔记不能无限堆积

系统 SHALL 把观察笔记视为需要治理的“评测资产”，而不是越积越多越好；进入样本池、负向约束池或经验池的内容都必须可追溯、可淘汰、可隔离。

### 原则 4：放行必须基于证据

系统 SHALL 让技能文件、提示词模板、记忆预算策略、观察笔记策略和模型路由的变更，都能基于基线样本、质量得分和 ROI 证据做放行，而不是只看单条效果。

## 词汇表

- **BenchmarkCase（基线样本）**：用于回放和对比的标准样本，可分为 `golden`、`bad_case`、`regression_guard` 三类。
- **GoldenCase（优质样本）**：代表平台希望稳定复现的高质量短剧样本。
- **BadCase（坏例样本）**：代表真实出现过的失败样本，用于防止相同问题复发。
- **RegressionGuard（回归守卫样本）**：对特定问题高度敏感的样本，如人物稳定性、情绪递进、镜头连续性。
- **ExperimentRun（实验运行）**：对一组样本按某个技能/提示词/记忆/模型配置执行的对比实验。
- **ExperimentVariant（实验变体）**：实验中的某一候选配置，如新提示词版本、新记忆预算策略或新模型路由。
- **BaselineVariant（基线变体）**：当前默认线上候选，作为所有比较的参照物。
- **JudgeRubric（评测量表）**：对人物一致性、情绪表达、镜头真实感、AI 痕迹、叙事抓力等维度的结构化评分规则。
- **PromotionGate（放行门）**：决定某个变更是否可以推广到更多项目的标准。
- **ObservationAsset（观察资产）**：从评审、返工、失败任务、人工复核中沉淀出的结构化观察项。
- **ObservationGovernance（观察治理）**：对观察项的去重、冲突检测、淘汰、归档和升降级管理。
- **MemoryBudgetProfile（记忆预算档）**：某种记忆预算配置快照，描述 `lean/expanded`、压缩规则、保留桶等策略。
- **ROIEvidence（ROI 证据）**：说明某次优化在 token 成本、通过率、返工率、坏例复发率上的收益证据。
- **ReviewQueue（复核队列）**：供运营或创作者人工二次判断的待审样本列表。

## 需求优先级

### P0：先补评测基建

- 基线样本池
- 实验运行记录
- 评分量表
- 人工复核队列
- 变更放行状态

### P1：再补实验与治理闭环

- 自动回放与对比
- 观察资产治理
- 记忆预算与 ROI 联动
- 样本升级与淘汰

### P2：最后补运营与发布策略

- 放行门
- 低 ROI 变更拦截
- 项目级灰度策略
- 长期质量趋势看板

## 需求

### 需求 1：基线样本池（BenchmarkCase Registry）

**用户故事：** 作为平台运营者，我希望把代表真实质量风险和高质量目标的短剧样本沉淀成标准样本池，这样后续任何优化都能回到同一批样本上做判断。

#### 验收标准

1. THE System SHALL 支持维护 `golden`、`bad_case`、`regression_guard` 三类基线样本。
2. EACH BenchmarkCase SHALL 至少记录 `project_id`、`script_id` 或等价业务范围、所属阶段、核心问题标签、样本类型、创建来源、创建人和最近验证时间。
3. WHEN 用户从质量评审、返工归因或任务失败记录中添加样本时，THE System SHALL 支持把当前对象升级为基线样本，并附带原因摘要。
4. THE System SHALL 支持为样本记录目标质量维度，如人物一致性、情绪递进、镜头连续性、反 AI 痕迹、台词自然度。
5. THE System SHALL 支持对样本设置权重或严重级别，以区分“必须守住”的回归守卫与普通参考样本。
6. IF 两个样本指向同一业务对象且问题标签高度重合，THEN THE System SHALL 提示可能重复，避免无限堆积。
7. THE System SHALL 保证样本的用户、项目与内容作用域可追溯，不允许跨用户误混用私有项目数据。

---

### 需求 2：实验运行与变体管理（ExperimentRun / Variant）

**用户故事：** 作为平台运营者，我希望在修改技能、提示词、记忆预算或模型策略后，能把变更放到同一批基线样本上做实验对比，而不是只凭感觉判断效果。

#### 验收标准

1. THE System SHALL 支持创建实验运行，并在一次实验中挂载一个基线变体和一个或多个候选变体。
2. EACH ExperimentVariant SHALL 至少记录技能版本、提示词版本、记忆预算档、观察治理策略版本、模型路由快照和备注说明。
3. WHEN 运营者发起实验时，THE System SHALL 支持选择样本集合、运行阶段范围和比较维度。
4. THE System SHALL 把实验输入快照固化，避免实验过程中因外部配置继续变更而污染结果。
5. WHEN 某个变体缺少必要依赖配置时，THE System SHALL 阻止进入运行态并返回缺失项说明。
6. THE System SHALL 支持实验状态流转：`draft`、`queued`、`running`、`completed`、`failed`、`cancelled`。
7. THE System SHALL 支持按项目隔离实验，不允许把 A 用户的记忆策略或私有观察资产直接混入 B 用户样本。

---

### 需求 3：分层回放与低成本实验策略

**用户故事：** 作为平台运营者，我希望实验不是每次都重跑完整流水线，而是按风险和改动范围只回放必要阶段，用更少 token 获得更可信的判断。

#### 验收标准

1. THE System SHALL 支持按阶段回放，如仅回放 `storyboard_table`、`storyboard_panel`、`video_prompt` 或更上游阶段。
2. WHEN 变更只影响提示词内控或记忆预算时，THE System SHALL 优先建议局部阶段实验，而不是默认整条流水线回放。
3. THE System SHALL 支持样本分层执行：`smoke`、`core`、`full` 三档。
4. THE System SHALL 优先复用已有中间产物、结构化快照和缓存，避免对同一样本无意义重复读取与重复注入。
5. THE System SHALL 记录每次实验相对“全量重跑”节省的 token 估算值。
6. IF 某次实验样本数量或阶段范围超出预设预算，THEN THE System SHALL 给出风险提示并允许缩小范围。
7. THE System SHALL 在质量风险高于成本节省时优先保留高风险样本和关键阶段，不允许为了省 token 删掉关键回归守卫。

---

### 需求 4：统一评测量表（JudgeRubric）

**用户故事：** 作为平台运营者，我希望平台对实验结果和人工复核都使用统一量表，这样“人物像不像 AI”“情绪是否自然”等判断不会飘来飘去。

#### 验收标准

1. THE System SHALL 定义统一评测维度，至少包含人物一致性、情绪表达、镜头真实感、视觉连续性、台词自然度、AI 痕迹、叙事抓力。
2. EACH 评测维度 SHALL 支持结构化分值、问题等级和文字说明。
3. THE System SHALL 支持为不同阶段配置不同的维度权重，如 `video_prompt` 更强调人物与情绪，`storyboard_table` 更强调节奏与连续性。
4. WHEN 自动评测无法给出高置信判断时，THE System SHALL 将样本转入人工复核队列，而不是输出伪精确分数。
5. THE System SHALL 支持记录“是否建议放行”“是否建议升为 bad case”“是否建议升为 golden case”等决策字段。
6. THE System SHALL 保证自动评分与人工复核共用同一问题类型字典，避免后续统计失真。
7. THE System SHALL 支持对同一实验变体输出汇总分与维度明细，便于后续 ROI 对比。

---

### 需求 5：人工复核队列（ReviewQueue）

**用户故事：** 作为平台运营者或创作者，我希望对高风险、自动判断不稳定、或价值很高的样本进行人工复核，这样平台的优化结论不会完全建立在自动打分上。

#### 验收标准

1. THE System SHALL 支持把自动评测低置信、分歧较大或关键样本加入人工复核队列。
2. EACH ReviewQueueItem SHALL 至少记录样本来源、实验运行、变体、待回答问题、优先级和截止时间。
3. THE System SHALL 支持复核人给出结构化评分、问题标签、建议动作和是否放行。
4. WHEN 同一样本已经存在未完成复核项时，THE System SHALL 避免重复创建等价复核任务。
5. THE System SHALL 支持复核结果回写到实验汇总、bad case 样本池和观察资产治理链路。
6. THE System SHALL 支持区分“内容质量复核”和“成本收益复核”两类复核任务。
7. THE System SHALL 保留复核审计信息，便于后续回溯某次放行为何成立。

---

### 需求 6：观察资产治理（ObservationGovernance）

**用户故事：** 作为平台运营者，我希望 bad case、评审备注、返工归因和人工观察不会无限增长，而是被治理成高信号资产，为后续提示词和记忆优化提供真正有用的输入。

#### 验收标准

1. THE System SHALL 支持把观察资产按来源分类：质量评审、任务失败、局部返工、人工复核、实验对比。
2. EACH ObservationAsset SHALL 至少记录问题类型、作用对象、信号强度、来源变体、来源样本、最近命中时间和当前状态。
3. THE System SHALL 支持对观察资产执行去重、冲突检测、低信号淘汰和归档。
4. WHEN 某条观察资产长期未命中或多次被证伪时，THE System SHALL 支持自动降级或进入归档候选。
5. WHEN 某条观察资产在多个 bad case 中重复命中，THE System SHALL 支持提升其优先级，并推荐进入默认负向约束或技能优化清单。
6. THE System SHALL 支持把观察资产与提示词诊断信息中的 `auto_negative_source`、`observation_note_chars`、`negative_budget_tier` 关联起来。
7. THE System SHALL 保证观察资产按用户、项目、风格包或全局模板边界明确隔离，避免不同用户项目相互污染。

---

### 需求 7：记忆预算档与 ROI 证据联动

**用户故事：** 作为平台运营者，我希望知道某个记忆预算策略到底值不值，哪些 `expanded` 真的带来了更自然的视频，哪些只是多烧 token。

#### 验收标准

1. THE System SHALL 支持把实验变体绑定到明确的 `MemoryBudgetProfile` 快照，而不是只记录模糊描述。
2. EACH MemoryBudgetProfile SHALL 至少记录预算层级规则、保留桶、压缩策略、观察笔记上限和角色记忆优先级。
3. THE System SHALL 支持在实验结果中比较不同预算档的 token 消耗、质量分布、返工率和 bad case 复发率。
4. WHEN 某个预算档显著增加 token 消耗但质量提升不明显时，THE System SHALL 将其标记为低 ROI 候选。
5. WHEN 某个预算档虽然更贵但能显著降低关键 bad case 复发率时，THE System SHALL 支持将其视为高价值策略。
6. THE System SHALL 允许按项目或风格类型查看“哪些场景需要 expanded，哪些只需 lean”的证据。
7. THE System SHALL 保证 ROI 对比使用同一批样本和同一放行量表，避免伪比较。

---

### 需求 8：变更放行门（PromotionGate）

**用户故事：** 作为平台运营者，我希望技能文件、提示词、记忆策略或模型路由的变更在推广前必须先经过质量和 ROI 放行，而不是改完就全量使用。

#### 验收标准

1. THE System SHALL 支持为实验变体输出放行状态：`blocked`、`needs_review`、`approved`、`approved_limited`。
2. THE PromotionGate SHALL 至少综合以下因素：基线样本通过情况、关键 bad case 是否复发、平均质量变化、严重问题变化、token 变化和人工复核结论。
3. IF 任一高权重回归守卫样本出现严重退化，THEN THE PromotionGate SHALL 默认阻断放行。
4. WHEN 质量提升明显但 token 成本显著上升时，THE System SHALL 支持给出“仅限高价值项目/高风险阶段启用”的有限放行建议。
5. THE System SHALL 支持把放行结果关联到具体技能版本、提示词版本或记忆策略版本。
6. THE System SHALL 记录放行决策说明、责任人和决策时间。
7. THE System SHALL 支持把已批准的变体推广为新的基线变体。

---

### 需求 9：长期趋势与回归监控

**用户故事：** 作为平台运营者，我希望能持续看到短剧质量、坏例复发和 token 效率的趋势，而不是只在某次实验里看一次数据。

#### 验收标准

1. THE System SHALL 支持按周或按版本查看质量总分、通过率、严重问题率、返工率和 token 效率趋势。
2. THE System SHALL 支持查看高频 bad case 类型排行和最近上升项。
3. THE System SHALL 支持查看观察资产命中率、被淘汰率和归档量变化。
4. THE System SHALL 支持查看记忆预算档的 ROI 排名和阶段适配度。
5. WHEN 某类关键问题在近期明显恶化时，THE System SHALL 支持触发回归告警或进入待复核状态。
6. THE System SHALL 支持按项目类型、风格包、模型和阶段做趋势切片。
7. THE System SHALL 保证趋势统计默认基于隔离后的聚合数据，避免暴露不必要的跨项目明细。

---

### 需求 10：Spec 边界与后续延展

**用户故事：** 作为项目维护者，我希望这个 spec 能清楚界定与现有质量优化 spec 的边界，避免重复建设，也为后续继续深入打基础。

#### 验收标准

1. THE System SHALL 复用现有质量评审、ROI 聚合、观察笔记治理和记忆预算诊断能力，不平行新造一套同义数据。
2. THE System SHALL 把本 spec 的重点放在“样本池、实验回放、统一量表、放行治理”，而不是重新实现已有的单次生成优化逻辑。
3. THE System SHALL 为后续引入视频文件级自动比对、素材视觉指纹、真人复核协作台和更细的模型路由实验预留扩展空间。
4. THE System SHALL 支持后续把放行结果接回项目级灰度配置，实现部分项目先用新策略、观察稳定后再全量推广。
5. THE System SHALL 支持后续把 bad case 样本进一步细分为“角色一致性守卫”“情绪表演守卫”“镜头语言守卫”“视频真实性守卫”。
6. THE System SHALL 支持后续把人工复核与运营 SOP 打通，而不要求本轮先实现复杂组织流。
7. THE System SHALL 保持与 `.kiro/specs/ai-drama-quality-optimization`、`.kiro/specs/drama-platform-completion` 的职责边界清晰。

## 附录 A：本轮 review 后确认的主要空白

1. 仓库里已有质量评审、ROI 聚合和观察笔记治理，但缺少 **稳定样本池**。
2. 仓库里已有技能版本、记忆预算和诊断字段，但缺少 **按同一输入做实验对比的运行框架**。
3. 仓库里已有统计能力，但缺少 **明确的放行门与灰度决策机制**。
4. 路线图文档已提到“自动化对比”“A/B”“bad case 回归”，但还没有独立 spec 把这件事完整落下来。

## 附录 B：与现有 spec 的关系

1. `ai-drama-quality-optimization` 负责生成链路本身的质量能力和技能规范。
2. `drama-platform-completion` 负责平台闭环、记忆预算、观察治理、ROI 和工作台能力。
3. `drama-quality-benchmark-ops` 负责把前两者沉淀成 **可比较、可复核、可放行** 的运营与评测体系。
