# 小说导入与爬虫专项计划

更新时间：2026-05-07

这个文档单独收口 Toonflow 平台里“小说原文接入”相关计划，覆盖手动录入、整本导入、客户端爬虫、后续服务端爬虫，以及它们与改写、分镜、生产链路的衔接规则。

## 目标

在不牺牲改编质量的前提下，把“小说原文进入平台”做成可运营、可追踪、可修正、可扩展的统一入口：

- 支持个人用户手动录入
- 支持整本原文一次性导入并自动切章
- 支持 `crawler_client` 自动抓取网页正文
- 后续支持 `server-side crawl` 作为增值能力
- 所有入口共享统一 intake 契约、准入状态和修正流程
- 为后续改写、事件抽取、骨架生成、剧本初稿生成提供稳定上游

## 当前已完成

已落地到主链的内容：

- `manual` 手动录入入口
- `whole-book import` 整本导入入口
- 本地预解析切章
- 导入前逐条修正：改标题、改正文、删误切、补漏切
- 导入前自动重排序号与空正文拦截
- `crawler_client` 首版：按 URL 抓网页、抽标题与正文、回填整本导入区
- `intake_source` / `intake_source_url` / `intake_status` / `intake_note`
- 手动、整本、客户端爬虫三条入口统一写入 intake 元数据
- 列表筛选与批量准入操作

## 统一 intake 模型

所有小说接入方式统一落到同一套 intake 语义：

- `intake_source`
  - `manual`
  - `import`
  - `crawler_client`
  - `crawler_server`（后置）
- `intake_source_url`
  - 原文来源地址
- `intake_status`
  - `pending_review`
  - `admitted`
  - `rejected`
- `intake_note`
  - 准入备注、异常说明、编辑说明

这样做的目的：

- 不把爬虫入口做成旁路
- 后续统计、筛选、审批、问题回溯共用一套数据
- 改写链路可以判断当前文本是否已准入

## 主链流程

统一主链：

1. 原文进入平台
2. 预解析 / 去噪 / 自动切章
3. 人工修正
4. 设置准入状态
5. 章节落库
6. 事件抽取 / 骨架生成 / 改写 guidance / 剧本初稿

### A. 手动录入

适用于：

- 用户自己粘贴章节
- 无法稳定抓取的网站
- 需要只录某几章做试跑

要求：

- 单章快速录入
- 可带来源备注
- 可直接标记 `pending_review` 或 `admitted`

### B. 整本导入

适用于：

- 用户已拿到整本文本
- 爬虫已在平台外完成

要求：

- 自动按章节标题切章
- 用户可逐条修正切章结果
- 导入前做空正文、序号、标题完整性校验

### C. `crawler_client`

适用于：

- 当前客户端可直接访问目标页面
- 希望先低成本跑通全自动导入

要求：

- URL 输入
- HTML 抽正文
- 标题抽取
- 回填到整本导入区，不直接强行入库
- 仍走统一修正与准入流程

当前策略：

- 客户端抓取只负责“获取原始文本”
- 不跳过人工修正页
- 先保证接入质量，再谈完全无人工

### D. `server-side crawl`（后置增值）

定位：

- 托管采集
- 批量抓取
- 定时抓取
- 作为付费增强能力

必须共享：

- 与 `crawler_client` 相同的 intake 契约
- 相同的准入状态流转
- 相同的导入修正页

这样可以避免以后两套爬虫两套后处理。

## 还需要补齐的计划点

> 2026-05-07 本轮已落地（代码已接入）：
>
> - `crawler_client` 新增“适配点”能力：同页正文抽取 + 分页发现（`nextPage`）+ 目录章节发现（`chapterUrls`）
> - 客户端抓取新增自适应策略：目录页按章节链接抓取、正文分页自动续抓、失败回退单页
> - 清洗层增强：常见站点噪音行过滤（广告/导航/版权/下一页提示）、特殊空白清理
> - 切章规则增强：补充 `序章` / `尾声` / `番外` 识别
> - 导入质量门接入导入动作：字数不足、平均章节过短、重复正文过高时阻断导入
> - intake 状态影响后续链路：`draft` / `pending_review` / `rejected` 章节禁止直接触发 `generate-events`
> - 后端事件生成新增兜底质量门：正文字数过短章节会被直接拦截，避免绕过导入页后进入高成本抽取
> - intake 来源契约后端白名单化：统一收敛到 `manual / whole_book_import / crawler_client / crawler_server`（兼容 `import` 别名）

### 1. 多来源抓取策略

状态：**已完成（client-side crawl v2）**

需要支持：

- 单章 URL
- 目录页 + 章节详情页
- 整本正文页
- 站内分页正文
- 异步加载正文

最少要做的不是“抓所有站”，而是把适配点抽出来：

- 页面抓取
- 标题抽取
- 正文抽取
- 下一页 / 下一章发现
- 目录发现

## 2. 内容清洗

状态：**已完成（统一清洗层已接入）**

爬虫结果必须进入统一清洗层，至少处理：

- 广告段
- 重复段落
- 导航文字
- 版权提示
- 页脚站点文案
- 异常空行
- 乱码或特殊空白字符

目标不是过度美化，而是减少脏文本进入改写链。

## 3. 切章可靠性

状态：**已完成第一阶段增强（含序章/尾声/番外识别）**

整本导入与爬虫导入都要面对切章问题。

需要继续完善：

- 常见章节标题模式识别
- “卷 / 章 / 节 / 番外 / 序章 / 尾声”识别
- 误把正文台词当标题的拦截
- 超长章节分块策略
- 极短章节合并提示

## 4. 导入质量门

状态：**已完成并接入导入动作（阻断 + 提示）**

进入后续改写前，建议有基础准入门：

- 是否有足够正文字数
- 是否章节数异常
- 是否存在大量重复内容
- 是否存在明显正文抽取失败
- 是否还处于 `pending_review`

不满足时，不应直接进入后续自动改写主链。

## 5. 多项目 / 多用户隔离

状态：**已完成（按 project/workspace 隔离）**

这是平台能力，不是单用户脚本。

必须保证：

- 爬虫结果按 `workspace/project` 隔离
- 不同项目的导入历史互不污染
- 同一用户多个项目可独立导入不同小说
- 企业多成员协作时可看到项目内导入历史，但不能串项目

## 6. 前端体验

状态：**已完成第一阶段（统一工作台内闭环）**

前端要尽量一步完成，不把用户赶去多个散入口。

建议最终入口形态：

- 小说工作台
  - 手动录入
  - 整本导入
  - URL 抓取
- 统一预解析页
- 统一修正页
- 统一准入页
- 统一批量入库页

用户心智应该是“导入小说”，不是先理解三套技术实现。

## 7. 可观测与审计

状态：**已完成第一阶段（导入模式/页数/质量提示可见）**

后续需要补：

- 导入来源统计
- 爬虫成功率
- 抽取失败原因
- 切章修正率
- 准入通过率
- 哪些来源最容易进入高质量改写链

这部分后续会直接影响是否值得上 `server-side crawl`。

## 8. 与改写链路的关系

状态：**已完成关键门禁（未准入章节拦截 generate-events）**

内容接入不是独立功能，直接影响后续质量。

必须保持：

- intake 文本不要直接整包喂给大模型
- 优先先压缩成章节摘要 / 事件 / 骨架 / guidance
- 长章节必须支持分块消费
- 未准入或抽取质量差的正文不要直接推入高成本改写

## 近期实施顺序

近期建议顺序：

1. 完善 `crawler_client` 清洗与切章稳定性
2. 增加导入质量门
3. 增加多来源抓取适配点
4. 让 intake 状态更明确影响后续改写主链
5. 再规划 `server-side crawl`

## 结论

当前“小说爬虫”还不能算完全完善。

现在已经完成的是：

- 首版客户端抓取
- 统一 intake 契约
- 导入修正
- 准入状态

还没完全收口的是：

- 多来源抓取适配
- 清洗层
- 切章可靠性增强
- 导入质量门
- 服务端托管爬虫
- 更完整的平台级可观测
