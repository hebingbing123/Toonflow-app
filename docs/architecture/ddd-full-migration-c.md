# 全仓 DDD 迁移（选项 C）— 实施计划（草案）

本文档描述：若决定在本仓库 **后端 `backend/`** 上实施 **选项 C（全仓按 DDD 思想重组领域层与应用层）**，建议的 **阶段划分、门禁、目标结构** 与 **风险**。  
**不是**要求立即执行；可作为评审用路线图。与 [`harness-rust-flutter.md`](../roadmaps/harness-rust-flutter.md) 的关系：**契约（OpenAPI / `docs/websocket-events.md`）与对外 URL 不变**；**Harness** 继续负责工具、权限、观测；**DDD 主要作用于「业务规则与持久化编排」在 Rust 代码中的落点**。

---

## 1. 选项 C 在本仓库的含义（边界）

| 维度 | 纳入 C | 不纳入或弱纳入 |
|------|--------|----------------|
| **HTTP/WS 契约** | 保持兼容；变更走版本化或单独 ADR | 不因「DDD」批量改名路由 |
| **Harness** | 边界清晰：领域结果 → 工具/会话层 | 不把 Harness 强行塞进「实体/聚合」教科书 |
| **竖切模块**（`projects/`、`narrative/`、`assets/`…） | 逐步变为 **应用服务 + 领域 + 基础设施** 的协作关系，而非仅 handler 堆叠 | 不要求一天内目录全换 |
| **数据模型** | 表结构以迁移演进为主；**领域模型 ≠ 表一一映射** | 不为 DDD 大规模重命名已上线列（除非业务需要） |

**完成定义（建议）**：核心业务路径上，**不变量与状态转换**可在 **无 IO 的模块** 中单元测试；HTTP handler **薄**（鉴权、反序列化、调用应用服务、映射错误）；`pg_contract_tests` 与 `yarn refactor:check` **持续绿**。

---

## 2. 前置条件（开工前一次性澄清）

1. **冻结或基线契约**：以合并 OpenAPI（`shell.rs` + 嵌入历史 schemas + 路径索引 + utoipa）、`docs/websocket-events.md` 为真源；任何破坏性变更必须显式记录（parity / 客户端同步）。
2. **选定「限界上下文」清单**：与现有竖切大致对齐即可（例如：项目与资产、叙事与剧本分镜、生产工作台、计费与用量、任务队列、设置与供应商凭证等）；允许 1～2 轮调整，避免无限命名辩论。
3. **命名与语言**：团队（或单人）统一使用 **中文讨论 / 英文代码符号** 的词汇表（Ubiquitous Language 的最小集），写在本文档附录或 `docs/glossary.md`（可选，**仅在有需要时**另建）。
4. **分支策略**：长周期迁移使用独立分支（如 `refactor/ddd-c`），**小步合并**到主重构分支，避免单次巨型 PR。

## 3. 目标分层（Rust 侧参考形态）

以下为 **参考目录/职责**，实施时可按模块渐进落地，不必一次到位。

```
backend/src/
  domain/                    # 纯领域：实体、值对象、领域服务、不变量（无 sqlx / axum）
    <context>/
      mod.rs
      aggregates/
      errors.rs
  application/               # 用例：编排、事务边界、权限前置校验的「业务入口」
    <context>/
      services.rs | ports.rs   # ports =  trait 抽象仓储/时钟/ID
  infrastructure/            # 适配器：sqlx 实现、外部 HTTP、文件系统
    persistence/
    <context>_repo.rs
  # 现有顶层竖切可逐步迁入或 facade：
  projects/  narrative/  assets/  ...  → 逐步变为 interface（HTTP）+ 委托 application
```

**原则**：

- **`domain`**：可单测、不依赖 Tokio 运行时（除极少数 `std` 外）。
- **`application`**：可依赖 `domain` + `ports`（trait）；实现放在 `infrastructure`。
- **`app/handlers` 或各模块 `http.rs`**：只做协议与 DTO ↔ 领域命令/查询的映射。

与 **Harness** 的交界：`application` 或专用 **facade** 将「领域执行结果」交给 `harness` 层序列化/观测，避免在 `domain` 里引用 WebSocket 类型。

## 4. 分阶段实施（推荐顺序）

### 阶段 0：基线与度量（约 0.5～1 天）

- 记录当前 **`cargo test`**、**`cargo clippy -D warnings`**、**`yarn refactor:check`** 基线。
- 列出 **最痛** 的 2～3 条业务路径（例如：项目删除级联、计费状态机、任务重试），作为 **首批** 领域化对象。

### 阶段 1：骨架与范例（1 个竖切试点）

- 在 **`domain` + `application` + `infrastructure`** 建立 **一个** 完整竖切（建议选 **规则集中、依赖清晰** 的模块，如 `metering` 或小型 `settings` 子域，而非最大模块）。
- 该竖切内：**新代码**走新分层；旧 handler 改为 **调用 application service**（薄适配）。
- **交付物**：该路径的 **领域单测** + 原有 **契约测试仍通过**。

### 阶段 2：绞杀者迁移（Strangler，按模块滚动）

对每个竖切重复：

1. 识别 **聚合根** 与 **跨聚合用例**（写操作尽量单事务、单聚合内强一致）。
2. 将 **SQL 与不变量** 从 handler 抽到 `domain` / `application` + `ports`。
3. `infrastructure` 实现 `ports`（sqlx）。
4. Handler 仅保留 HTTP 映射。
5. **每合并一次**：跑 `yarn refactor:check`；涉及 PG 的变更跑 **`pg_contract_tests`**（`DATABASE_URL` 等）。

**顺序建议**（可按依赖调整）：**计费/订阅状态机**、**任务与幂等**、**项目/资产**、**叙事线**、**生产工作台**、其余。

### 阶段 3：横切关注点

- **错误映射**：`domain::Error` → `crate::error::ApiError`（或现有错误类型）集中映射，避免每层字符串散落。
- **事务**：在 `application` 层明确 **一个用例 = 一个事务**（`sqlx::Transaction` 在 infrastructure 或 application 边界注入）。
- **幂等与并发**：与现有 `jobs`、webhook 逻辑对齐，领域层表达 **意图**，基础设施保证 **唯一约束 / 去重**。

### 阶段 4：收尾与删除死代码

- 删除不再被调用的「旧直写 SQL 路径」。
- 文档：在 [`harness-rust-flutter.md`](../roadmaps/harness-rust-flutter.md) 或本文档 **更新「后端分层」小节**（一段话即可）。
- **完成定义复核**：见 §1 完成定义。

## 5. 测试与门禁（必须）

| 门禁 | 用途 |
|------|------|
| `yarn refactor:check` | 与 CI `refactor-monorepo` 对齐；见根目录 [`AGENTS.md`](../../AGENTS.md) |
| `backend` 单元测试 | `domain` / `application` 纯逻辑优先 |
| `app::pg_contract_tests` | 需 PG 的契约回归；`#[ignore]` 测试在可连库时执行 |
| OpenAPI / WS 文档 | 对外行为变更时同步更新 |

**禁止**：长时间「新目录已建、旧路径仍为主路径」却不跑通全链路——每个迭代至少 **一条** 端到端路径在新架构下可演示。

## 6. 风险与缓解（详细）

### 6.0 风险与「解决方案」的关系（先读）

- 下文中的 **「缓解」与「解决方案（可执行）」指同一类内容**：**流程、约束、门禁、代码结构**，用来 **降低风险发生的概率或后果**；**不是**「没有对策」。
- 架构迁移类风险一般 **无法从根上消灭**（例如迁移期必然短暂双轨），目标是 **可验收地管住**：有清单、有门禁、有「算完成」的标准。
- 若某条风险 **复发**，对应做法是 **回到同一套解决方案重做或补强**（例如补测试、缩 PR、拆事务），而不是换一套玄学命名。

**速览：风险 → 核心解决方案 → 怎么算到位（验收）**

| 风险 | 核心解决方案 | 验收（做到哪步算解决） |
|------|----------------|------------------------|
| 双轨混乱 | 试点竖切 + 绞杀者删除旧路径 + 每 PR 可测 | 该模块 **仅一条主写路径**；旧代码已删或薄委托 |
| 过度设计 | 只抽不变量；ports/YAGNI | 新增简单 CRUD **≤2～3 个文件** 能改完；无空壳类型 PR |
| 单人迷路 | 词汇表 + 固定目录约定 + 测行为 | 新人/未来的你 **5 分钟内** 找到「改某业务规则」的入口 |
| Harness 耦合 | `domain` 不依赖 harness；DTO/facade | `cargo tree` 或模块依赖 **无** domain→harness |
| 事务/一致性 | 用例级事务；跨聚合用事件/编排文档化 | 无「半写入」类 bug；跨聚合有 **明确最终一致** 说明 |
| 性能/观测 | 热路径对比；批量查询显式；错误映射 | 关键接口延迟 **不明显劣化**；错误仍带 `request_id` |
| 回归空洞 | `refactor:check` + PG 契约 + 小 PR | 合并前门禁绿；里程碑前 **跑过** 相关 `pg_contract_tests` |

各小节仍保留 **现象 / 为何要命 / 预警信号**；**「解决方案（可执行）」** 为对应条目的展开清单。

### 6.1 迁移周期过长、双轨混乱

**现象**：新旧两套「写业务」的方式并存——有的地方走 `application`，有的仍在 handler 里直写 SQL；时间久了 **同一规则改两处**，行为漂移，排查时要猜「这次请求走的是哪条链」。

**在本仓库为何突出**：竖切已经按功能分模块，若再叠一层「半完成的 domain」，目录变多但 **主路径未切过去**，比完全不迁更乱。

**解决方案（可执行）**：

- **先试点再铺开**：第一个竖切从入口到持久化 **走通一整条**，再复制模式到其他模块。
- **绞杀者（Strangler）**：每个模块迁移的完成定义是 **旧路径删除或仅保留薄委托**，而不是「新目录有了就算」。
- **合并纪律**：每次 PR **必须**绿 `yarn refactor:check`；动到 DB 行为则跑 **`pg_contract_tests`**（环境允许时）。

**预警信号**：连续多周「新分层只有目录和类型，线上逻辑仍全在旧 handler」；或同一 bug 修了 A 忘了 B。

---

### 6.2 过度设计、样板爆炸

**现象**：为「像 DDD」而引入大量 `Entity`/`Repository` 空壳、每层只做透传，**行数与文件数暴涨**，真正的不变量仍散落在 SQL 字符串里。

**为何要命**：单人或小团队时，**导航与修改成本**上升，收益却接近零；后期会产生「不敢删层」的技术债。

**解决方案（可执行）**：

- **只把「会写错第二次」的东西放进 domain**：状态机、跨字段不变量、计费/订阅顺序规则、幂等键语义等；简单的 CRUD 不必硬造聚合。
- **拒绝贫血模型**：若实体只有 getter/setter 与 ORM 映射，说明这层可以不存在或合并。
- **YAGNI**：没有第二个实现前，`ports` 不必为每个方法拆一个 trait；可从一个 `XxxStore` trait 或单模块 `impl` 起步。

**预警信号**：新增一个简单接口要改 6 个文件；或 PR 里 80% 是 `pub struct` 与 `impl` 样板。

---

### 6.3 单人维护、认知负荷过高

**现象**：目录深、命名多（`XxxService` / `XxxUseCase` / `XxxHandler` 职责不清），**自己三个月后回来也迷路**。

**解决方案（可执行）**：

- **一页纸词汇表**（Ubiquitous Language 最小集）：项目里「剧本 / 分镜 / 资产 / 任务 / 订阅状态」等与代码模块的对应关系固定下来。
- **约定优于配置**：例如「写操作用例一律在 `application::<ctx>::commands`」「读模型查询在 `queries`」——选一种并写进本文档或 `AGENTS.md` 补充。
- **投资测试而非投资层数**：优先保证 **契约测试 + 关键领域单测**；分层是手段，可回归才是目的。

**预警信号**：每次加功能要先想「该放哪一层」超过想「业务规则是什么」。

---

### 6.4 与 Harness 耦合

**现象**：为了「方便」，在 `domain` 里引用 `harness::ws`、工具名、会话 ID 类型，或领域错误里塞前端可读文案。**结果**：改工具协议或 WS 时牵动「业务核心」，单测必须 mock 整棵 Harness。

**解决方案（可执行）**：

- **依赖方向**：`domain` / `application` **不**依赖 `harness`；由 **接口层或 application 边缘** 把领域结果转成 Harness 可用的 DTO。
- **显式 facade**：例如 `ScriptWorkspaceBridge` 只负责「领域输出 → tool result 形状」，便于替换与单测。

**预警信号**：`cargo tree` 里 `domain` 包（或模块）反向依赖 `harness`。

---

### 6.5 事务边界与跨聚合一致性搞错

**现象**：把本该 **一个事务** 内的写拆成多个 application 调用，中间失败导致 **半写入**；或把 **跨聚合** 的强一致硬塞进单聚合事务，锁与死锁风险上升。

**解决方案（可执行）**：

- **默认**：一个 HTTP 命令 / 一个 job 步骤对应 **明确的事务边界**（在 `application` 或 infrastructure 入口处打开 `Transaction`）。
- **跨聚合**：用 **领域事件 + 异步补全**、或 **显式编排**（saga/流程表），并在文档里写清「允许短暂不一致」的读路径。
- 与现有 **`jobs` worker、webhook 去重** 对齐：领域表达 **意图**（例如「应用订阅状态迁移」），基础设施保证 **幂等与唯一约束**。

**预警信号**：「有时能复现有时不能」的数据错乱；或 PG 日志里同一请求多条独立 `COMMIT` 本应合一。

---

### 6.6 性能与可观测性退化

**现象**：分层后多轮克隆 DTO、重复查库、tracing span 断层，**延迟上升**或 **错误难定位**。

**解决方案（可执行）**：

- 对 **热路径**（列表、高频轮询、WS 附带的读）做 **前后对比**（`tracing`、粗粒度计时）。
- **批量读/写** 仍在 infrastructure 层显式存在，避免「纯领域」导致 N+1 查询被藏进抽象里。
- 保持现有 **`X-Request-Id`** 与错误 JSON 映射习惯，领域错误类型 **映射到** `ApiError`，不在深层 `println!`。

**预警信号**：明显可感的接口变慢；或日志里只剩「application 某层失败」没有 SQL/业务原因。

---

### 6.7 迁移期回归空洞

**现象**：重构 PR 很大，**契约测试没跑**或只跑了 `cargo test` 里不触 DB 的部分，**线上 parity 悄悄坏了**。

**解决方案（可执行）**：

- **门禁不降级**：合并前 `yarn refactor:check`；涉及行为变更时同步 **OpenAPI / WS 文档**。
- **PG 契约**：本地或 CI 有 DB 时跑 `pg_contract_tests`；至少关键路径在里程碑前跑通一轮。
- **小步合并**：宁可多几个 PR，也不要一个「三个月一次性合并」。

**预警信号**：「应该没改行为」但 Flutter 或脚本依赖的字段悄悄变了；或 `#[ignore]` 测试长期没人跑。

---

## 7. 估算（数量级，非承诺）

- **试点竖切**：约 **数天～两周**（视模块复杂度）。
- **全仓 C**：通常 **数月** 量级（取决于业务路径数量与是否并行产品功能）；**单人** 时建议 **拉长周期、减小每步合并体积**。
