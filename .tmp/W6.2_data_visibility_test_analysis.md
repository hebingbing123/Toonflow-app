# W6.2: 测试 owner/member/outsider 三种身份的数据可见性

## 任务概述

- **Owner**: 工作空间所有者

- **Outsider**: 非工作空间成员

### 角色权限分析

#### 1. Owner (工作空间所有者)
✅ **完全访问权限**
- 可以看到工作空间基本信息
- 可以看到工作空间成员列表
- 可以看到所有项目及其相关资源（脚本、资产、小说、任务）
- 无法看到其他用户的个人数据（agent_memory, art_style）

#### 2. Member (工作空间成员)
⚠️ **受限访问权限**
- 可以看到工作空间基本信息
- 可以看到工作空间成员列表
- **无法看到项目相关数据**（这是当前 RLS 策略的预期行为）
- 无法看到其他用户的个人数据

#### 3. Outsider (非成员)
❌ **无访问权限**
- 无法看到任何工作空间相关数据
- 完全被 RLS 策略阻止访问

## RLS 策略分析

### 当前 RLS 策略概览

1. **app_workspace**: `app_workspace_member_access` - 通过成员表验证访问权限
2. **app_workspace_member**: `app_workspace_member_self` - 仅能看到自己的成员记录
3. **app_project**: `app_project_own` - 仅项目所有者可见
4. **项目相关表** (script/asset/novel): 通过项目所有者验证
5. **app_generation_job**: `app_generation_job_own` - 仅任务所有者可见
6. **个人数据表**: 仅个人所有者可见

### 预期不匹配 (Expected Mismatch) 说明

标记为 `expected_mismatch` 的表格反映了当前架构设计：

- **RLS 层面**: 采用保守的 owner-only 策略作为安全护栏
- **应用层面**: Rust 后端实现更细粒度的 workspace 成员权限
- **设计意图**: RLS 作为最后防线，应用层提供实际的业务权限逻辑

## 与 Rust 应用层的关系

### 权限架构设计

```
┌─────────────────┐    ┌──────────────────┐    ┌─────────────────┐
│   Flutter UI    │───▶│  Rust Backend    │───▶│   PostgreSQL    │

│ 用户交互        │    │ 业务权限逻辑     │    │ RLS 安全护栏    │

```

### 双层权限验证

1. **应用层 (Rust)**: 实现 workspace 成员可以访问项目数据的业务逻辑
2. **数据库层 (RLS)**: 提供 owner-only 的安全护栏，防止应用层绕过

### 预期行为差异

| 场景 | RLS 行为 | Rust 应用层行为 | 说明 |
|------|----------|----------------|------|
