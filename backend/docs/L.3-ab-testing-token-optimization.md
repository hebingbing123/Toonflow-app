# L.3 A/B Testing Framework for Token Optimization Validation

## Overview

This document describes the A/B testing infrastructure implemented to validate that Phase J token optimizations (J.1-J.6) don't cause quality regressions. The framework compares baseline (pre-optimization) implementations against optimized implementations to ensure token savings are achieved without compromising quality.

**Implementation**: Task L.3 from spec "短剧生成完善化"  
**Phase**: L - Production Acceptance Re-Run

## Architecture

### Components

1. **A/B Testing Framework** (`backend/src/publish/ab_testing.rs`)
   - Variant management (baseline vs optimized)
   - Quality metrics tracking
   - Token usage metrics tracking
   - Comparison logic with configurable thresholds
   - Statistical validation

2. **Database Storage** (`app_ab_test_results` table)
   - Persistent storage of test results
   - Audit trail for all A/B tests
   - Time-series analysis support

3. **Test Suite** (`backend/src/publish/ab_testing_tests.rs`)
   - Comprehensive validation tests
   - Phase J optimization validation
   - Quality regression detection
   - Token reduction verification

## Key Concepts

### Variants

Two variants are compared in each A/B test:

1. **Baseline** - Pre-optimization implementation
   - No caching (J.1)
   - Full regeneration for all platforms (J.2)
   - No usage logging optimization (J.3)
   - No request aggregation (J.4)
   - Full fanout for project overview (J.5)
   - No request deduplication (J.6)

2. **Optimized** - Phase J optimized implementation
   - Input hash cache enabled (J.1)
   - Incremental mode for changed platforms (J.2)
   - LLM usage logging (J.3)
   - Aggregated publish requests (J.4)
   - Reduced loadProjectOverview fanout (J.5)
   - Request deduplication and generation protection (J.6)

### Quality Metrics

Quality is measured across multiple dimensions:

- **Overall Score** (0-100): Aggregate quality score
- **Character Consistency** (0-100): Character appearance and behavior consistency
- **Dialogue Naturalness** (0-100): Natural and contextually appropriate dialogue
- **Visual Quality** (0-100): Visual fidelity and production quality
- **Plot Coherence** (0-100): Story logic and narrative flow
- **Grade** (A/B/C/D): Letter grade for overall quality
- **Passed** (boolean): Whether quality gate passed

### Token Metrics

Token usage is tracked comprehensively:

- **Prompt Tokens**: Input tokens sent to LLM
- **Completion Tokens**: Output tokens generated by LLM
- **Total Tokens**: Sum of prompt and completion tokens
- **Call Count**: Number of LLM API calls made
- **Cache Hits**: Number of cache hits (J.1 optimization)
- **Incremental Hits**: Number of incremental mode uses (J.2 optimization)

## Configuration

### Default Thresholds

```rust
ABTestConfig {
    min_token_reduction_pct: 10.0,  // Minimum 10% token reduction required
    max_quality_drop: 5.0,           // Maximum 5 point quality drop allowed
    min_quality_score: 70.0,         // Minimum acceptable quality score
    significance_threshold: 0.05,    // Statistical significance threshold
}
```

### Customization

Thresholds can be customized per test case:

```rust
let config = ABTestConfig {
    min_token_reduction_pct: 20.0,  // Require 20% reduction
    max_quality_drop: 3.0,           // Allow max 3 point drop
    min_quality_score: 75.0,         // Higher quality bar
    significance_threshold: 0.01,    // Stricter significance
};
```

## Pass/Fail Criteria

A test passes if ALL of the following conditions are met:

1. **Token Reduction**: `token_reduction_pct >= min_token_reduction_pct`
2. **Quality Maintenance**: `quality_drop <= max_quality_drop`
3. **Minimum Quality**: `optimized_score >= min_quality_score`
4. **Grade Maintenance**: Grade doesn't regress (A > B > C > D)
5. **Pass Status**: If baseline passed, optimized must also pass

## Usage

### Running A/B Tests

```bash
# Run all A/B testing tests
cd backend
cargo test --package toonflow-server --lib publish::ab_testing_tests -- --nocapture

# Run specific test
cargo test test_j1_input_hash_cache_validation -- --nocapture
```

### Programmatic Usage

```rust
use crate::publish::ab_testing::*;

// Create test results
let baseline = ABTestResult {
    test_case_id: "publish-copy-test-001".to_string(),
    variant: ABVariant::Baseline,
    quality: QualityMetrics { /* ... */ },
    tokens: TokenMetrics { /* ... */ },
    timestamp: Utc::now(),
    metadata: json!({}),
};

let optimized = ABTestResult {
    test_case_id: "publish-copy-test-001".to_string(),
    variant: ABVariant::Optimized,
    quality: QualityMetrics { /* ... */ },
    tokens: TokenMetrics { /* ... */ },
    timestamp: Utc::now(),
    metadata: json!({}),
};

// Compare variants
let config = ABTestConfig::default();
let comparison = compare_variants(&baseline, &optimized, &config);

if comparison.passed {
    println!("✓ Test passed: {}% token reduction, {} quality change",
        comparison.token_reduction_pct,
        comparison.quality_score_diff.unwrap_or(0.0)
    );
} else {
    println!("✗ Test failed:");
    for reason in &comparison.failure_reasons {
        println!("  - {}", reason);
    }
}
```

### Database Integration

```rust
// Store test results
let baseline_id = store_ab_test_result(&pool, &baseline).await?;
let optimized_id = store_ab_test_result(&pool, &optimized).await?;

// Fetch results for comparison
let results = fetch_ab_test_results(&pool, "publish-copy-test-001").await?;
let baseline = results.get(&ABVariant::Baseline).unwrap();
let optimized = results.get(&ABVariant::Optimized).unwrap();

// Fetch metrics from production data
let quality = fetch_quality_metrics(&pool, job_id).await?;
let tokens = fetch_token_metrics(&pool, job_id).await?;
```

## Test Coverage

The test suite validates each Phase J optimization:

#### J.1: Input Hash Cache
- **Test**: `test_j1_input_hash_cache_validation`
- **Validates**: Cache hits reduce tokens without quality loss
- **Expected**: 30-50% token reduction with cache hits

#### J.2: Incremental Mode
- **Test**: `test_j2_incremental_mode_validation`
- **Validates**: Incremental generation reduces tokens
- **Expected**: 30-50% token reduction with incremental hits

#### J.3: LLM Usage Logging
- **Validated by**: Token metrics tracking
- **Ensures**: All LLM calls are logged for cost analysis

#### J.4: Request Aggregation
- **Validated by**: Call count reduction
- **Ensures**: Multiple requests are aggregated

#### J.5: Reduced Fanout
- **Validated by**: Token reduction in project overview
- **Ensures**: Duplicate fetches are eliminated

#### J.6: Request Deduplication
- **Validated by**: Call count and cache hit tracking
- **Ensures**: Duplicate requests are deduplicated

### Quality Regression Detection

The test suite validates quality regression detection:

1. **Overall Score Drop**: Detects significant quality score drops
2. **Grade Regression**: Detects grade downgrades (A→B, B→C, etc.)
3. **Pass/Fail Regression**: Detects quality gate failures
4. **Below Minimum**: Detects quality below acceptable threshold
5. **Individual Metrics**: Tracks character consistency, dialogue, visual quality, plot coherence

### Token Reduction Validation

The test suite validates token reduction:

1. **Minimum Reduction**: Ensures minimum token savings achieved
2. **Cache Effectiveness**: Validates cache hit rates
3. **Incremental Effectiveness**: Validates incremental mode usage
4. **Combined Optimizations**: Validates multiple optimizations together

## Integration with Existing Systems

### Quality Gate System (Phase I)

The A/B testing framework integrates with the quality gate system:

- Uses same quality metrics (overall_score, grades, etc.)
- Validates quality gate pass/fail status
- Ensures optimizations don't bypass quality gates

### Token Tracking (J.3)

The framework integrates with LLM usage logging:

- Fetches token metrics from `app_llm_usage_log`

- Correlates token usage with quality scores

## Production Usage

### Staging Environment Testing

Before deploying Phase J optimizations to production:

1. **Baseline Collection**: Run tests with optimizations disabled
2. **Optimized Collection**: Run tests with optimizations enabled
3. **Comparison**: Compare results using A/B framework
4. **Validation**: Ensure all tests pass before production deployment

### Continuous Validation

In production:

1. **Periodic Testing**: Run A/B tests weekly/monthly
2. **Regression Detection**: Alert on quality regressions
3. **Optimization Tuning**: Adjust optimization parameters based on results
4. **Cost Analysis**: Track token savings over time

## Database Schema

### app_ab_test_results Table

```sql
CREATE TABLE app_ab_test_results (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    test_case_id TEXT NOT NULL,
    variant TEXT NOT NULL CHECK (variant IN ('baseline', 'optimized')),
    quality_metrics JSONB NOT NULL DEFAULT '{}'::jsonb,
    token_metrics JSONB NOT NULL DEFAULT '{}'::jsonb,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Indexes

- `idx_ab_test_results_test_case_id`: Fast lookup by test case
- `idx_ab_test_results_variant`: Fast lookup by variant
- `idx_ab_test_results_created_at`: Time-series queries
- `idx_ab_test_results_test_case_variant`: Composite lookup

## Troubleshooting

### Common Issues

1. **Test Fails with Insufficient Token Reduction**
   - Check if optimizations are enabled
   - Verify cache is populated
   - Check incremental mode is working

2. **Test Fails with Quality Regression**
   - Review quality metrics for specific issues
   - Check if quality gate thresholds changed
   - Verify baseline quality is acceptable

3. **Missing Quality Metrics**
   - Ensure quality reviews are created
   - Check job_id linkage
   - Verify quality gate is enabled

4. **Missing Token Metrics**
   - Ensure LLM usage logging is enabled (J.3)
   - Check job_id linkage
   - Verify calls are being logged
