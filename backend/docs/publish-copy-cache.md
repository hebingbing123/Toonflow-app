# Publish Copy Cache (J.1 & J.2) and Usage Logging (J.3)

## Overview

The publish copy cache reduces redundant LLM calls by caching publish copy generation results based on input hash. When the same draft content and target platforms are requested again, the cached result is returned instead of making a new LLM call.

All publish copy generation calls are logged to `app_llm_usage_log` for cost tracking and optimization analysis (J.3).

## Incremental Mode (J.2)

The publish copy generation now operates in incremental mode, only regenerating copy for platforms that have changed:

### Platform Diff Detection

When `suggest_platform_copy_fragment` is called, it compares:
- **Existing platforms**: Keys in the draft's `platform_copy` field
- **Target platforms**: Platforms in the current targets list

This produces three sets:
- **Added**: New platforms that need copy generation
- **Removed**: Old platforms no longer in targets (copy will be excluded)
- **Unchanged**: Platforms that already have copy and are still in targets

### Generation Strategy

1. **No added platforms**: If all current targets already have copy, return existing copy immediately (source: "incremental")
2. **Some added platforms**: Generate copy only for added platforms, preserve existing copy for unchanged platforms
3. **First generation**: All platforms are treated as "added", full generation occurs

### Cache Behavior

- Cache keys are computed based on **only the platforms being generated** (not all platforms)
- This allows cache hits even when platform sets differ
- Example: If you have copy for [douyin, xiaohongshu] and add [bilibili], only bilibili's generation is cached

### Benefits

1. **Token savings**: Only generate copy for new platforms, not all platforms
2. **Consistency**: Existing platform copy remains unchanged unless explicitly regenerated
3. **Performance**: Instant return when no platforms added
4. **Cache efficiency**: Smaller cache keys for partial generations

## Implementation

### Database Schema

Table: `app_publish_copy_cache`

- `id`: UUID primary key
- `input_hash`: TEXT (unique) - SHA256 hash of input parameters
- `platform_copy_fragment`: JSONB - Generated platform copy
- `source`: TEXT - Generation source ('llm', 'fallback', 'cache', or 'incremental')
- `created_at`: TIMESTAMPTZ - When the cache entry was created
- `last_used_at`: TIMESTAMPTZ - Last time this cache entry was used
- `use_count`: INTEGER - Number of times this cached result has been used

### Hash Computation

The input hash is computed from:
- Draft title
- Draft description
- Draft tags (sorted for stability)
- Target platform IDs (sorted for stability) - **only platforms being generated**
- Style hint (if provided)

The hash is stable across different orderings of tags and platforms, ensuring cache hits for equivalent inputs.

### Cache Flow

1. **Platform Diff**: Compute which platforms are added/removed/unchanged
2. **Incremental Check**: If no platforms added, return existing copy (source: "incremental")
3. **Cache Lookup**: For added platforms, compute input hash and check cache
4. **Cache Hit**: If found, update `last_used_at` and `use_count`, merge with existing copy
5. **Cache Miss**: Generate copy via LLM or fallback for added platforms only
6. **Merge**: Combine newly generated copy with existing unchanged platform copy
7. **Response**: Return merged copy with source indicator

### API Response

The `SuggestPlatformCopyResponse` includes a `source` field that indicates:
- `"incremental"`: No generation needed, returned existing copy for all platforms
- `"cache"`: Generated platforms were retrieved from cache, merged with existing
- `"llm"`: Generated platforms were freshly generated by LLM, merged with existing
- `"fallback"`: Generated platforms used fallback template, merged with existing

## Benefits

1. **Cost Reduction**: Eliminates redundant LLM calls for identical inputs (J.1) and unchanged platforms (J.2)
2. **Performance**: Cached and incremental results return instantly without LLM latency
3. **Consistency**: Same inputs always produce same outputs; unchanged platforms keep their copy
4. **Metrics**: `use_count` tracks cache effectiveness

## Cache Invalidation

- Manual cache clearing per project
- Cache size limits with LRU eviction
- Platform spec version tracking

## LLM Usage Logging (J.3)

All publish copy generation calls are logged to `app_llm_usage_log` with the following information:

### Logged Metadata

- **user_id**: User making the request
- **call_type**: `"publish_copy_generation"`
- **model_name**: LLM model used (e.g., "gpt-4o") or "fallback" for template-based generation
- **provider**: LLM provider (e.g., "openai", "anthropic") if applicable
- **Token counts**: `prompt_tokens`, `completion_tokens`, `total_tokens` (from LLM API response)
- **duration_ms**: Total call duration including cache lookup and LLM call
- **success**: `true` for successful generation, `false` for errors
- **error_message**: Error details if generation failed

### Context in Meta Field

The `meta` JSONB field includes:
- `draft_id`: UUID of the publish draft
- `project_uuid`: UUID of the project (note: `project_id` field is NULL as publish uses UUID-based projects)
- `source`: Generation source ("llm", "cache", "incremental", or "fallback")
- `cache_hit`: Boolean indicating if result came from cache
- `platforms_generated`: Array of platform IDs that were generated (empty for incremental with no changes)
- `style_hint`: Optional style hint provided by user

### Usage Scenarios

1. **LLM Generation**: Full token usage logged with `source: "llm"`
2. **Cache Hit**: No token usage, fast response with `source: "cache"` and `cache_hit: true`
3. **Incremental (No Changes)**: No token usage, instant return with `source: "incremental"`
4. **Fallback**: No token usage, template-based with `source: "fallback"` and `model_name: "fallback"`
5. **Error**: No token usage, error details logged with `success: false`

### Cost Analysis

The logged data enables:
- Token consumption tracking per user/project
- Cost estimation when pricing data is available
- Cache effectiveness analysis (cache hits vs. LLM calls)
- Incremental mode savings measurement
- Error rate monitoring

### Privacy

The logging does not include:
- Draft content (title, description, tags)
- Generated platform copy
- User prompts or LLM responses

Only metadata and token counts are logged for cost tracking purposes.
